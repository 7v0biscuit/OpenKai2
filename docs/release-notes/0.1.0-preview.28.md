This preview fixes an extra display wait inside native movie decoding. The
Movie playback was slow and could freeze during the transition afterward. Its shutdown log leaves the movie worker at priority 1 with
67,613 queued wakeups while the main thread cannot finish its handoff.

The original CRI player already schedules picture presentation. The host decoder
also waited for VBlank, yielding the synchronous worker to the main thread's
resume/wake loop. Accumulated wakeups then made the worker's SleepThread return
immediately, preventing the main thread from restoring normal scheduling.
Native decoding now returns buffered pictures synchronously. The generic MPEG
adapter keeps its existing presentation pacing. A bounded end-of-stream report
records how many pictures were returned.

The regression reproduces the previous runtime's failure with generated MPEG-2
input: all pictures decode, but the worker accumulates wakeups and completes no
main-loop cycles. The corrected runtime handles the final picture and EOF,
restores main-thread priority, and completes eight original service/sleep cycles
without queued wakeups. Tests cover both padded input and the original SDK/CRI
refill callback, plus decoded pixels and memory bounds at 32x32 and 512x448.
The installed Windows application must pass this scheduling check before release.
